# Dual Auth Provider Plan

## Goal

Support Google and Microsoft login through one standardized authentication system.

The final model should not treat Google as the default identity shape with Microsoft bolted on. Providers should be interchangeable implementations behind a small auth-provider contract, and the application should own its user identity independently from any external provider.

This plan covers application login only. Optional product integrations such as Google Calendar and Microsoft Outlook Calendar should continue to use `integration_connections` and stay separate from login.

## Current State

Application login currently works like this:

```txt
desktop auth UI
  -> Electron opens /auth/start?platform=desktop
  -> backend starts Google OAuth
  -> Google redirects to /auth/callback
  -> backend creates or updates users row
  -> backend creates Firebase custom token
  -> web callback opens orion://auth-complete?code=...
  -> Electron exchanges code at /auth/complete
  -> renderer signs into Firebase with custom token
```

Important current constraints:

- `/auth/start` always uses Google.
- `/auth/callback` assumes Google.
- `users.id` is currently the OAuth provider user ID for users created by Google login.
- Firebase custom tokens use `users.id` as the Firebase UID.
- Account linking is inferred by email, not stored as a durable provider identity.
- `user_oauth_tokens` stores login OAuth tokens but is not a provider identity model.
- Calendar integration is being moved to `integration_connections`, which is the correct separate model for provider integrations.

## Target Architecture

### Identity Layers

Use three distinct concepts:

```txt
Application user
  Stable Orion-owned user record.
  Stored in users.
  Used as Firebase UID and backend user_id.

Auth identity
  External login identity linked to an application user.
  Stored in user_auth_identities.
  Examples: Google subject, Microsoft oid/sub.

Integration connection
  Optional provider account/token access for product features.
  Stored in integration_connections.
  Examples: Google Calendar, Outlook Calendar, Drive, OneDrive.
```

Rules:

- Login proves who the user is.
- Integrations grant access to external product data.
- Login tokens and integration tokens must not share tables.
- Provider IDs must never be used as the long-term application identity.
- The callback URL can be shared across providers because provider choice is stored in OAuth state.

### Canonical Flow

```txt
GET /auth/start?provider=google&platform=desktop
GET /auth/start?provider=microsoft&platform=desktop

backend:
  validate provider
  create random state
  store state payload in Redis:
    purpose=app_login
    provider=google|microsoft
    platform=desktop|web
  redirect to provider authorization URL

provider:
  redirects to /auth/callback?code=...&state=...

backend:
  consume state
  resolve provider from state
  exchange code using provider implementation
  normalize profile
  resolve or create application user
  upsert auth identity
  create or update Firebase user
  create Firebase custom token
  create one-time app auth code
  redirect to frontend callback

desktop:
  receives orion://auth-complete
  exchanges one-time app auth code
  signs into Firebase with custom token
```

## Provider Contract

Each login provider should implement one internal contract.

```go
type AuthProvider interface {
	Name() models.AuthProvider
	Config() *oauth2.Config
	AuthCodeURL(state string) string
	Exchange(code string) (*oauth2.Token, *NormalizedAuthProfile, error)
}
```

Normalized profile:

```go
type NormalizedAuthProfile struct {
	Provider        models.AuthProvider
	ProviderUserID  string
	Email           string
	EmailVerified   bool
	DisplayName     string
	AvatarURL       string
	RawClaims       map[string]any
}
```

Provider implementations:

```txt
backend/internal/auth/providers/google.go
backend/internal/auth/providers/microsoft.go
backend/internal/auth/providers/registry.go
```

The OAuth handler should call the registry, not provider-specific functions:

```go
provider, ok := providerRegistry.Get(statePayload.Provider)
profile, token, err := provider.Exchange(code)
```

No handler branch should directly know Google or Microsoft endpoints except through provider implementations.

## Data Model

### Users

Target rule:

```txt
users.id is an app-owned opaque ID.
```

Use UUIDs generated by Postgres or the backend.

```sql
-- Target new-user behavior.
id text primary key default gen_random_uuid()::text
```

Existing users may currently have Google IDs as `users.id`. That should be fixed as part of the full consistency migration described below.

### Auth Identities

Add a table for provider login identities.

```sql
create table if not exists user_auth_identities (
  id uuid primary key default gen_random_uuid(),
  user_id text not null references users(id) on delete cascade,
  provider text not null,
  provider_user_id text not null,
  provider_email text,
  email_verified boolean not null default false,
  display_name text,
  avatar_url text,
  raw_claims jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  last_login_at timestamptz,
  constraint user_auth_identities_provider_check
    check (provider in ('google', 'microsoft')),
  constraint user_auth_identities_unique_provider_subject
    unique (provider, provider_user_id),
  constraint user_auth_identities_unique_user_provider
    unique (user_id, provider)
);

create index if not exists user_auth_identities_user_id_idx
  on user_auth_identities (user_id);

create index if not exists user_auth_identities_provider_email_idx
  on user_auth_identities (provider, lower(provider_email));
```

Why both unique constraints:

- `(provider, provider_user_id)` prevents one external account from linking to multiple Orion users.
- `(user_id, provider)` keeps one login identity per provider per app user for now.

If a future provider supports multiple login identities per user under the same provider, revisit `unique (user_id, provider)`.

### Login Tokens

Do not store login OAuth tokens unless there is a product requirement.

Application login only needs:

- provider identity
- verified email
- display profile
- Firebase custom token

`user_oauth_tokens` should be deprecated for login auth. Product access tokens belong in `integration_connections`.

If login refresh tokens become necessary later, add a separate table keyed by `user_auth_identities.id`, not by `(user_id, provider)`.

## User Resolution

Resolve login in this order:

```txt
1. Find user_auth_identities by provider + provider_user_id.
   If found, use that user.

2. If no identity exists, require a trustworthy email.
   Email must come from an OIDC/userinfo source and should be verified when provider exposes verification state.

3. Find existing users row by lower(email).
   If found, link this provider identity to that user.

4. If no user exists, create a new app-owned user ID.
   Then insert provider identity.
```

Case-insensitive email matching should be standardized. The current repository uses exact email matching; the migration should add or adopt a lower-cased lookup to avoid duplicate accounts caused by casing.

If a provider returns no email, or an unverified email where verification is required, reject login unless a provider-specific policy explicitly allows it.

## Provider Details

### Google

Login scopes:

```txt
openid
email
profile
```

Provider user ID:

```txt
OIDC sub, or Google userinfo id if that is the current source.
```

Preferred target is OIDC `sub` because it is the standard subject claim.

### Microsoft

Login scopes:

```txt
openid
email
profile
offline_access
User.Read
```

Provider user ID:

```txt
Microsoft oid if available; otherwise OIDC sub.
```

Use one rule consistently in code and store the selected value in `provider_user_id`.

Recommended:

- Use `oid` for Entra/work accounts when present.
- Fall back to `sub` for personal Microsoft accounts if `oid` is absent.
- Store raw claims so future migration/debugging is possible.

Microsoft OAuth endpoints should live in the Microsoft provider implementation, not in the shared handler.

## URL Design

Use one shared login callback:

```txt
/auth/callback
```

Start URL selects provider:

```txt
/auth/start?provider=google&platform=desktop
/auth/start?provider=microsoft&platform=desktop
```

The OAuth callback must not trust a provider query parameter. It must read provider from Redis state created by `/auth/start`.

Backward compatibility:

```txt
/auth/start?platform=desktop
```

can default to Google until all desktop code calls the generic provider API.

## Future Web Platform

The current implementation should target desktop only, but the auth model should keep `platform` separate from `provider`.

Provider answers:

```txt
Who authenticated the user?
google | microsoft | future login providers
```

Platform answers:

```txt
Where should the completed app session return?
desktop | web | future clients
```

The OAuth provider should always redirect back to the backend-owned callback:

```txt
/auth/callback
```

The backend should then route the one-time app auth code to the correct client callback based on the `platform` stored in OAuth state.

Current scope:

```txt
platform=desktop
```

Future web scope:

```txt
platform=web
```

Adding web note viewing/editing later should not require a new identity table, provider-specific callback path, or separate provider implementation. It should only require platform-specific callback routing and a web client that consumes `/auth/complete`.

## Desktop API Design

Prefer one generic Electron API:

```ts
authenticate(provider: 'google' | 'microsoft'): Promise<AuthResult>
```

Short-term compatibility can keep:

```ts
authenticateWithGoogle()
authenticateWithMicrosoft()
```

but both should call the same internal helper.

The renderer should not know provider callback URLs. It should only request a provider login and handle the common auth completion result.

## Backend Implementation Plan

1. Add auth provider enum/model types.
2. Add `user_auth_identities` model and repository.
3. Add provider registry.
4. Move Google OAuth exchange behind the provider contract.
5. Add Microsoft provider implementation.
6. Extend login OAuth state with `provider`.
7. Update `/auth/start` to accept provider and use provider registry.
8. Update `/auth/callback` to resolve provider from state and normalize profile.
9. Replace `createOrUpdateUser` with provider-agnostic identity resolution.
10. Stop storing login tokens in `user_oauth_tokens` unless explicitly needed.
11. Update Firebase create/update to use app-owned user ID.
12. Update Electron API and auth UI.

## Full Consistency Migration

To make both Google and Microsoft fully consistent, migrate to app-owned user IDs for every user.

### Why This Is Needed

Without this migration:

- Existing users keep Google-shaped IDs.
- New users can use app-owned IDs.
- The code can treat all IDs as opaque, but the database contains mixed historical ID formats.

Mixed historical IDs can work, but it is not the cleanest target if the goal is a standardized identity model.

### Migration Strategy

Create a temporary mapping table:

```sql
create table auth_user_id_migration_map (
  old_user_id text primary key,
  new_user_id text not null unique default gen_random_uuid()::text
);

insert into auth_user_id_migration_map (old_user_id)
select id from users
on conflict do nothing;
```

Backfill current Google identities before changing IDs:

```sql
insert into user_auth_identities (
  user_id,
  provider,
  provider_user_id,
  provider_email,
  email_verified,
  created_at,
  updated_at
)
select
  m.new_user_id,
  'google',
  u.id,
  u.email,
  true,
  now(),
  now()
from users u
join auth_user_id_migration_map m on m.old_user_id = u.id
where u.deleted_at is null
on conflict (provider, provider_user_id) do nothing;
```

Then update every table that references `users(id)` from old ID to new ID.

Known user-owned tables should be discovered from the live schema before writing the migration. Based on the current repo, expect at least:

```txt
users
user_oauth_tokens
integration_connections
calendar_preferences
notes
folders
conversations
messages
recording sessions
transcript segments
note versions
note attachments
```

The migration should use database metadata to verify every foreign key that references `users(id)` has been handled.

After all referencing tables are updated:

```sql
update users u
set id = m.new_user_id
from auth_user_id_migration_map m
where u.id = m.old_user_id;
```

Firebase impact:

- Firebase UID cannot be changed in place.
- After migration, backend creates custom tokens using the new app user ID.
- Users will sign into a new Firebase UID on next login.
- Old Firebase Auth user records can be left orphaned or cleaned up later by an admin script.
- Local Firebase persistence may hold the old UID until logout/re-login; the desktop lifecycle should force a fresh custom-token sign-in after OAuth completion.

Run this migration only when the app can tolerate a forced re-login.

## Transitional Option

If a full user ID migration is too risky immediately:

- Add `user_auth_identities`.
- Backfill Google identities with `user_id = users.id` and `provider_user_id = users.id`.
- Generate app-owned IDs for new users only.
- Treat all user IDs as opaque everywhere.

This is operationally safer but leaves mixed historical ID formats. It should be considered a bridge, not the final standardized model.

## Security Requirements

- OAuth state must be random, single-use, and short-lived.
- Callback provider must come from stored state, never request query params.
- Log provider and high-level status only; do not log auth codes, access tokens, refresh tokens, or full callback URLs.
- Validate allowed provider names through a central enum.
- Require HTTPS redirect URLs outside local development.
- Normalize and validate email before account linking.
- Prefer verified emails for automatic account linking.
- Do not silently link accounts when two providers return different verified emails.
- Keep login scopes minimal.
- Keep integration scopes separate from login scopes.

## Testing Plan

Backend tests:

- `/auth/start` defaults to Google when provider is omitted.
- `/auth/start` accepts Google and Microsoft.
- `/auth/start` rejects unknown providers.
- `/auth/callback` uses provider from state.
- Invalid or expired state fails.
- Existing identity login resolves the same user.
- New provider with same verified email links to existing user.
- New provider with new email creates a new app user.
- Duplicate provider identity cannot create duplicate users.
- Unverified or missing email follows provider policy.

Desktop tests:

- Google login still succeeds.
- Microsoft login succeeds.
- Cancelled provider login returns to auth UI.
- Login timeout still resets pending state.
- Logout destroys signed-in windows and returns to signed-out state.

Migration tests:

- Every table referencing `users(id)` is updated.
- Existing Google users can log in after migration.
- Firebase custom token UID equals the new app user ID.
- Calendar connections remain attached to the same logical user.

Manual provider tests:

- Google account creates a user.
- Microsoft account creates a user.
- Google then Microsoft with same verified email lands in same user.
- Microsoft then Google with same verified email lands in same user.
- Different emails create different users.

## Rollout Plan

1. Add `user_auth_identities` while Google remains the only visible provider.
2. Backfill Google identities.
3. Refactor Google login through provider registry.
4. Run Google regression tests.
5. Add Microsoft provider behind a feature flag.
6. Test Microsoft with local Azure app registration.
7. Enable Microsoft in desktop auth UI for development builds.
8. Decide whether to run full user ID migration before production release.
9. Enable Microsoft in production only after identity linking and migration behavior are confirmed.

## Final Invariants

- `users.id` is the only application user ID.
- `users.id` is app-owned and provider-neutral.
- Firebase UID equals `users.id`.
- External provider IDs live only in `user_auth_identities`.
- Login OAuth implementation is provider-pluggable.
- Product integration tokens live only in `integration_connections`.
- Login scopes and integration scopes are separate.
- Adding a new login provider should require a provider implementation, registry entry, config, and UI label only.
